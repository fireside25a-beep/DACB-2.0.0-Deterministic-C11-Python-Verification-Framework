# Independent digital twin contract

The Python implementation exists to test implementation independence, not to serve as the canonical runtime.

## Independence requirements

The twin must not:

- import DACB C code through FFI;
- execute the DACB C binary;
- read canonical output generated by C;
- load generated C vectors as its source of truth;
- share mutable state with the C process.

The current twin satisfies those rules. It contains its own sequential evaluator, affine exponentiation, matrix exponentiation, inverse arithmetic, exhaustive traversal, semantic-regression implementation, audit logic, and report serializer.

## Identity requirements

The release verifier starts each executable independently and captures its bytes. `cmp` is then used externally.

Canonical identity currently covers:

```text
GCC C11 report == Clang C11 report == Python twin report
GCC C11 5000-step line == Clang line == Python line
GCC C11 1M-step line == Clang line == Python line
C11 2..11 exhaustive line == Python 2..11 exhaustive line
```

This does not mean the C and Python binaries themselves are byte-identical. It means their **canonical observable verification outputs** are byte-identical.
